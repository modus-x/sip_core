# Синхронизация метаданных с координатами участников с медиа-потоком

# Проблематика

Разрезка кадра от SIP-ядра, которое является организатором видео-конференции выполняется на стороне клиента

Координаты отправляются в SIP, а видео-поток в RTP

Каким образом синхронизировать разрезку по новым координатам с приходящими RTP-пакетами, чтобы не было артефактов в видео?

# Обсудили голосом 

Проработать решение: привязаться к временным меткам

# Решили проверить теорию в ИИ

## DeepSeek

### Вопрос 

Предложи решение для такой ситуации:
MCU-сервер получает видео-потоки (RTP) от нескольких SIP-клиентов - участников конференции.
MCU-сервер собирает один общий видео-поток из видео каждого участника, склеивая их в один прямоугольную картинку с черными полями на пустом месте и отправляет её по RTP каждому участнику (на каждый SIP-клиент приходит одинаковая картинка). Данные отправляют по протоколу SIP в команде SIP NOTIFY.
Кроме общей картинки MCU отправляет всем SIP-клиентам участникам координаты вершин изображения каждого участника внутри общей картинки. SIP-клиенты умеют вырезать из общей картинки отдельные куски каждого участника и размещать их на экране в произвольном порядке.
Когда к конференции подключается новый участник, то очевидно что координаты изображений участников меняются.
Каким образом синхронизировать момент начала применения новых координат на стороне SIP-клиентов и момент отправки RTP-потока с новым участником и новым набором координат всех участников?

### Ответ 

Вот несколько решений, от наиболее правильного и надежного до более простых.

### [Решение 1 (Рекомендуемое): Использование RTP-заголовка (Timestamp и SSRC)](#решение-1-рекомендуемое-использование-r)

Это самое корректное решение, так как оно использует встроенные механизмы RTP и не зависит от задержек в SIP-сигнализации.

**Как это работает:**

- **Подготовка новых координат:** MCU готовит новый макет (layout) с новыми координатами для всех участников.
- **Ключевой элемент — Temporal Alignment:** MCU связывает новый макет с **конкретным моментом во временной шкале RTP-потока**. Для этого он определяет будущий **RTP Timestamp**, начиная с которого новый макет должен быть применен.
- **Отправка уведомления (SIP NOTIFY):**MCU отправляет SIP NOTIFY всем участникам.
- В теле NOTIFY (например, в XML-документе) передаются: Новые координаты для каждого SSRC (источника).
- **Критически важный параметр: rtp-timestamp**. Это значение RTP Timestamp, начиная с которого клиенты ДОЛЖНЫ применить новые координаты.
- Можно также передать ssrc общего видеопотока, к которому относятся координаты (на случай, если у кого-то их несколько).

**Пример XML в NOTIFY:**

<conference-layout version="123">

  <video-ssrc>123456789</video-ssrc>

  <valid-from-rtp-timestamp>9876543210</valid-from-rtp-timestamp>

  <participant>

    <ssrc>111111</ssrc>

    <x>0</x>

    <y>0</y>

    <width>640</width>

    <height>360</height>

  </participant>

  <participant>

    <ssrc>222222</ssrc>

    <x>640</x>

    <y>0</y>

    <width>640</width>

    <height>360</height>

  </participant>

  <!-- ... и так далее ... -->

</conference-layout>

- **Синхронизация на стороне клиента:**Клиент получает NOTIFY. Он видит параметр valid-from-rtp-timestamp.
- Клиент продолжает отображать видео по старому макету.
- Клиент начинает "следить" на заголовками входящих RTP-пакетов общего видеопотока.
- Как только он получает пакет с RTP Timestamp **большим или равным** значению valid-from-rtp-timestamp, он мгновенно применяет новый макет для отображения этого и всех последующих пакетов.

**Почему это решение надежное:**

- **Независимость от задержки SIP:** Неважно, пришел NOTIFY раньше или позже RTP-пакетов. Клиент ждет конкретную метку в самом медиапотоке.
- **Точная синхронизация:** Все клиенты переключатся на новый макет **одновременно** (в контексте одного и того же кадра видео), так как они ориентируются на один и тот же RTP Timestamp.
- **Отсутствие артефактов:** Не будет ситуации, когда клиент пытается вырезать фрагмент по новым координатам из кадра, закодированного в соответствии со старым макетом.

### [Решение 2: Использование маркера в медиапотоке (Payload Marker)](#решение-2-использование-маркера-в-медиа)

Это менее элегантное, но рабочее решение, если по каким-то причинам нельзя использовать временные метки.

- **Маркировка ключевого кадра:** MCU, когда готов перейти на новый макет, генерирует ключевой кадр (Intra-frame, I-frame). Он помечает этот кадр, установив **RTP Marker (M) бит** в заголовке RTP-пакета, который является первым пакетом этого ключевого кадра.Примечание: Спецификация RTP для видео разрешает использовать Marker бит для обозначения конца кадра, но на практике его часто можно интерпретировать и как начало ключевого, если это оговорено заранее. Лучше использовать кастомный сигнал в NOTIFY, как ниже.

- **Согласованный сигнал:** В SIP NOTIFY MCU отправляет новые координаты вместе с инструкцией: **"Применить новый макет к первому полученному ключевому кадру (I-frame), следующему после получения этого сообщения"**.
- **Действия клиента:**Получает NOTIFY.
- Запоминает новые координаты.
- Ждет прихода RTP-пакета, который является частью ключевого кадра (это определяется по SDP-параметрам, например, packetization-mode и sprop-parameter-sets для H.264, или по наличию IFrame в данных).
- При получении первого ключевого кадра применяет новый макет.

**Недостатки этого решения:**

- Зависит от частоты ключевых кадров. Если ключевой кадр будет только через 10 секунд, переключение макета затянется.
- Требует от клиента более сложной логики парсинга видеопотока.
- Менее точно по времени, чем метод с временной меткой.

### [Решение 3 (Простое, но ненадежное): Использование задержки (Buffering)](#решение-3-простое-но-ненадежное-использ)

Это "костыльное" решение, которое можно использовать, если клиенты "тупые" и не поддерживают advanced-фичи.

- MCU вносит искусственную **задержку в исходящий RTP-поток**, например, на 500 мс.
- При смене макета MCU: Рассылает NOTIFY с новыми координатами.
- Ждет 300-400 мс (давая NOTIFY время дойти до всех).
- Начинает кодировать и отправлять видео с новым макетом в этот задержанный RTP-поток.

**Недостатки:**

- **Ненадежно:** В сетях с большой переменной задержкой (jitter) NOTIFY все равно может опоздать.
- **Добавляет латенси:** Искусственная задержка ухудшает качество взаимодействия.
- **Всплывающие артефакты:** Высока вероятность появления на клиенте "мусора" на экране в момент переключения.

Это надежно решает проблему "гонки" между сигнальным сообщением и медиапотоком.
