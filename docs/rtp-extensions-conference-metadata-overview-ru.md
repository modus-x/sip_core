# Передача метаданных конференции через RTP-расширения вместо SIP INFO

**Аудитория:** коллеги и руководство. **Статус:** проектное предложение (обзор).
**Связанные документы:** технический план реализации — `docs/rtp-extensions-conference-metadata-plan-en.md` (для разработчика/ИИ-агента, на английском). Исходный анализ проблемы — `Синхронизация+метаданных+с+координатами+участников+с+медиа-потоком.md`.

---

## 1. Проблема

В видеоконференции сервер-микшер (MCU) склеивает видео всех участников в **один общий кадр** (мозаику) и рассылает его по RTP. Клиент должен вырезать из этого общего кадра прямоугольник каждого участника и разложить плитки по экрану. Для этого клиенту нужны **координаты каждой плитки** внутри общего кадра.

Сегодня эти координаты (и голосовая активность) передаются **отдельно от видео — по SIP** (технически — телом **in-dialog SIP INFO** с типом `application/confInfo+json`; метод INFO строится в `im::sendSipMessage`, `src/im/instant_messaging.cpp:156-157` — отладочный лог на `:172` ошибочно пишет «SIP MESSAGE»). SIP-сигнализация и RTP-медиа идут по **разным путям с разной задержкой**.

**Гонка, которая ломает картинку:** когда организатор меняет раскладку (или входит/выходит участник), новый видеокадр по RTP приходит **раньше**, чем SIP-сообщение с новыми координатами. Клиент какое-то время режет **новый** кадр по **старым** координатам → визуальные артефакты (сдвинутые/обрезанные плитки, «мусор» на стыках).

Косвенное подтверждение того, что SIP — неподходящий транспорт для этих данных, уже есть в коде: голосовую активность приходится **искусственно придерживать (throttle)**, потому что частая отправка по SIP приводит к срабатыванию флуд-защиты SIP-сервера и разрыву соединения (`Conference::sendVoiceActivity`, `src/conference.cpp:908`).

---

## 2. Решение

Автор нашего RTP-сервера добавил поддержку **RTP-расширений заголовка (RTP header extensions, RFC 8285)**. Это позволяет прикреплять небольшие метаданные **прямо к RTP-пакету** с видео/аудио.

Ключевое свойство: метаданные, вложенные в RTP-пакет, **синхронизированы с кадром по построению** — они несут ту же RTP-временную метку, что и пиксели, которые описывают. Гонка «SIP отстал от RTP» исчезает: координаты приезжают ровно с тем кадром, к которому относятся.

Переносим на RTP-расширения три вида событий (по предложению коллеги):

| ID | Событие | Данные | На каком потоке |
|----|---------|--------|-----------------|
| `0x01` | **Метка A/V-синхронизации** | 64-битная NTP-метка времени захвата (`abs-capture-time`) | **всегда, на аудио И видео** |
| `0x02` | **Координаты участника** | индекс участника + прямоугольник плитки (x,y верхнего-левого и нижнего-правого углов). **URI внутри НЕ передаётся** — см. §4.5 | видео, по изменению |
| `0x03` | **Голосовая активность** | битовая маска: 1 бит на участника (говорит/молчит) | видео, по изменению |

> **Размер расширения ограничен не сервером, а MTU.** Автор RTP-сервера подтвердил: жёсткого лимита нет, теоретически можно слать данные любой длины, но слишком большой пакет превысит MTU и вызовет фрагментацию/потери. По стандартам предел на один элемент — 255 байт (RFC 8285), на всё расширение — ~256 КБ (RFC 3550), но реально ограничивает **MTU** (RFC 8085). **Рекомендация:** держать весь пакет ≤ ~1200 байт и резервировать под расширение фиксированные **≈128 байт**. При этом URI участника (до 246 байт) в `0x02` мы всё равно **не кладём** — не из-за лимита, а чтобы (1) не отъедать полезную нагрузку на каждом пакете и (2) не светить URI в открытом виде (расширения под SRTP не шифруются). `0x02` несёт только **индекс + координаты**, а привязка «индекс → участник (streamId/URI)» идёт **отдельным низкочастотным каналом** (по SIP). Подробнее — §4.5 и технический план.

### Важно: `0x01` решает отдельную задачу — синхронизацию звука и видео

Событие `0x01` (метка времени захвата в формате NTP) присутствует **на каждом пакете и аудио, и видео, всегда** — независимо от раскладки. Оно решает **самостоятельную** проблему: у аудио- и видеопотоков разные RTP-часы со случайным сдвигом, и без общей «настенной» метки времени их нельзя точно свести (классически для этого нужны RTCP Sender Reports, которые приходят редко и с запозданием). `abs-capture-time` кладёт общее время захвата прямо в каждый пакет, что даёт точную синхронизацию губ/звука без ожидания RTCP. Это подтверждается устройством нашего медиастека: на приёме RTP-временная метка выводится из PTS кадра со случайным сдвигом, поэтому абсолютное время захвата из неё восстановить нельзя — событие `0x01` действительно необходимо, а не опционально.

## 3. Как это работает (общая логика)

1. **Согласование по SDP.** При установлении звонка стороны договариваются о расширениях стандартными строками SDP:
   ```
   a=extmap:1 http://www.webrtc.org/experiments/rtp-hdrext/abs-capture-time
   a=extmap:2 urn:svetets:participant-info
   a=extmap:4 urn:svetets:voice-activity
   ```
   `extmap:1` (A/V-синхронизация) — на аудио **и** видео; `extmap:2/4` — только на видео. Если собеседник не подтвердил расширение в ответе — оно не используется (и работает откат на старый механизм).

2. **Отправка.** Хост/MCU при изменении раскладки формирует событие `0x02`/`0x03` и вкладывает его в RTP-расширение исходящих видеопакетов. Метка `0x01` кладётся в каждый пакет аудио и видео. События изменения **дублируются 3 раза** (RTP ненадёжен) — это рекомендованный стандартом способ повысить вероятность доставки.

3. **Приём.** Клиент читает расширение из RTP-пакета **ещё до декодирования видео**, извлекает координаты/голос/метку времени и применяет их к соответствующему кадру. Поскольку данные и кадр несут одну RTP-метку, «нарезка» всегда идёт по правильным координатам.

### Техническое решение по интеграции (две ключевые развилки)

- **Не патчим FFmpeg.** Наш медиастек использует RTP-мультиплексор FFmpeg (libavformat), а вокруг него — собственный «мост» `socket_pair.cpp`, который отдаёт/принимает уже готовые RTP-пакеты (и делает SRTP). Мы вставляем/читаем расширение именно в `socket_pair.cpp` — это **единственная точка**, где виден целый RTP-пакет, она общая для аудио и видео, для отправки и приёма, и **не зависит от кодека**. Патчить FFmpeg (rtpenc/rtpdec) было бы хуже: он не видит наши данные на отправке, **выбрасывает** расширения на приёме, и патч пришлось бы сопровождать при каждом обновлении FFmpeg. Вставка расширения делается **до** SRTP-шифрования (SRTP штатно оставляет расширение в открытом виде, но подписывает его — менять SRTP не нужно).
- **`abs-capture-time` на обоих потоках** получается «бесплатно», потому что аудио и видео проходят через один и тот же код `socket_pair.cpp`.

## 4. Что важно знать руководству: это не «просто поменять транспорт»

Глубокий анализ кода выявил, что наивная замена «SIP → RTP-расширение» **сама по себе артефакт не устранит** и не покроет все текущие данные. Ниже — честный список того, что нужно сделать правильно. Это не блокеры, а объём работ, который надо заложить.

### 4.1. Гибридный транспорт: часть данных остаётся на SIP

Текущее сообщение `confInfo` несёт ~18 полей на участника. RTP-события `0x01/0x02/0x03` «из коробки» покрывают только **геометрию плитки, индекс участника, голосовую активность и метку времени**. Остальное (поднятая рука, микрофон вкл/выкл, модератор, запись, режим раскладки, размеры холста и т.д.) **артефактов не вызывает** — иконка «поднятой руки» с задержкой 100 мс визуально безвредна — и его невыгодно гнать по ненадёжному RTP.

**Важное исключение — «видео выключено» (videoMuted) — это НЕ декорация, а управление.** От него зависит создание/удаление плитки на клиенте. Поэтому «присутствие» плитки определяется **по составу снимка раскладки в RTP** (индекс есть в снимке → плитка есть; индекса нет → плитка удаляется). Так «выключил видео / вышел» доезжает синхронно, а на SIP остаётся только *иконка* mute как декорация.

**Рекомендация:** переносим на RTP только то, что должно быть синхронно с кадром (координаты, присутствие, голос, A/V-метка). Остальную «декоративную» информацию и **ростер «индекс → участник (streamId/имя/URI)»** оставляем на SIP `confInfo`. Два канала связываются по **индексу**.

Отдельно: **команды управления от клиента к хосту** (`confOrder` — поднять руку, замьютить, выгнать участника, сменить активного докладчика) **обязаны остаться на SIP** — они должны доставляться надёжно, а у клиента нет гарантированного встречного медиапотока, куда их вложить.

### 4.2. Идентификатор плитки — это поток, а не URI

Клиент режет кадр и сопоставляет плитки по **идентификатору потока (streamId/sinkId)**, а не по URI. У одного участника может быть **два потока** (камера + демонстрация экрана) — по URI их не различить. Чтобы не раздувать расширение (оно вычитается из полезной нагрузки на каждом пакете) и не светить URI, событие `0x02` несёт компактный **индекс**, а привязка «индекс → поток (streamId)» приходит **по SIP** (низкочастотно). Клиент по индексу из RTP находит нужный поток и режет кадр. Правила выделения индексов задаёт автор RTP-сервера (владелец микшера).

### 4.3. Метка времени кадра теряется в декодере — нужен «боковой канал»

Наш декодер **перезаписывает** RTP-метку кадра на локальное «настенное» время (`media_decoder.cpp:860`). Значит, привязать метаданные к кадру «по совпадению временной метки после декодирования» **нельзя** — метка к этому моменту уже потеряна. Нужно пронести RTP-метку/поколение раскладки в обход декодера **как боковые данные кадра (AVFrame side-data)** — так метаданные едут вместе с кадром и переживают отбрасывание «поздних» кадров декодером; и применять координаты **атомарно вместе с кадром**. Иначе тот же артефакт вернётся на один слой ниже (текущая «нарезка» применяет координаты как отдельное изменяемое состояние в гонке между потоками).

### 4.4. Счётчик поколений против переупорядочивания и потерь

RTP переставляет и теряет пакеты. Дублирование «3 раза» помогает от потерь, но не от того, что **устаревшее** событие придёт после свежего. Нужно добавить в события раскладки **счётчик поколений (версию)**: клиент применяет только строго более новое поколение. Каждое поколение — **полный снимок** всех плиток. Пока раскладка помещается в один пакет (≈до 11 плиток при резерве 128 байт, см. §4.5), любого одного дошедшего экземпляра свежего поколения достаточно, чтобы восстановить раскладку. Если плиток больше, снимок **разбивается на фрагменты** (с общим номером поколения); клиент применяет поколение, только когда пришли все его фрагменты, а дублирование ×3 и следующее изменение раскладки страхуют от потери отдельного фрагмента.

### 4.5. Размер расширения (MTU) и стоимость по трафику

Жёсткого лимита у сервера нет; ограничивает **MTU** (RFC 8085): весь IP-пакет не должен его превышать, иначе фрагментация → потери и отбрасывание на NAT/firewall. Стандартные потолки: один элемент ≤ 255 байт (RFC 8285), всё расширение ≤ ~256 КБ (RFC 3550) — оба нерелевантны на фоне MTU.

- **Рекомендация по размеру.** Держать весь RTP/UDP/IP-пакет **≤ ~1200 байт** (безопасное для интернета значение, ниже IPv6-порога 1280; на заведомо локальной сети можно ~1400). Под расширение резервировать фиксированные **≈128 байт** (на видео; на аудио ~18 байт — там только `0x01`). Это резерв **на каждом** пакете (иначе кодировщик не оставит места), поэтому его держат небольшим — отсюда индекс вместо URI и пагинация координат.
- **Ёмкость.** В 128 байт помещается метка `0x01` плюс координаты **до ~11 участников** одним пакетом. При большем числе плиток координаты **разбиваются на фрагменты** (с общим номером поколения; клиент применяет раскладку, когда пришли все фрагменты). Порог настраиваемый (кратно 4, **но не выше 256 байт**): больше → меньше фрагментов, но выше «налог» на полезную нагрузку. Выше ~256 байт один элемент `0x02` упрётся в предел 255 байт на элемент (RFC 8285).
- **Постоянная надбавка.** Событие `0x01` присутствует на **каждом** аудио- и видеопакете (~16 байт на линии). Это заметная, но приемлемая постоянная надбавка; резерв под расширение (≈128 байт) вычитается из бюджета полезной нагрузки, чтобы пакет не превысил MTU.
- **Согласовать с автором RTP-сервера:** целевой размер пакета/MTU и то, что формат `0x02` без URI (с номером поколения и фрагментацией) поддерживается обеими сторонами.

### 4.6. Конфиденциальность

Под обычным SRTP шифруется **полезная нагрузка, но не заголовок и не расширения** — расширения едут в открытом виде даже при включённом SRTP. **Именно поэтому URI участников вынесены из `0x02`** (в расширении едут только индекс и координаты — не персональные данные), а привязка «индекс → участник» идёт по SIP. Если понадобится скрыть и координаты — потребуется шифрование расширений (RFC 6904); предлагаю вынести за рамки первой версии, но зафиксировать риск. (Дополнительно: в текущем коде настройка SRTP закомментирована, так что потоки могут идти как обычный `RTP/AVP` — тем более расширения в открытом виде.)

## 5. Этапы внедрения (предлагаемый roadmap)

1. **SDP-согласование** `a=extmap` (объявление + разбор ответа) и проброс согласованных ID в медиауровень. Пока без изменения RTP — по-настоящему изолированный и безопасный первый шаг.
2. **Проверка сосуществования (spike):** уточнить у автора RTP-сервера, шлёт ли он своё расширение `0xBEDE` (abs-send-time для управления перегрузкой). По стандарту в пакете допустимо только **одно** расширение, поэтому наши метаданные и abs-send-time не могут ехать двумя блоками — нужно решить, как их совместить, чтобы не сломать текущее управление перегрузкой. Это надо сделать до вставки `0x01`.
3. **A/V-синхронизация (`0x01`)** — ценная и относительно изолированная часть: вставка/чтение `abs-capture-time` на аудио и видео. Даёт синхронизацию звука/видео независимо от раскладки. **С этого же этапа** нужно заложить резерв под расширение (≈128 байт из бюджета MTU): раз `0x01` едет на каждом пакете, без резерва пакет может превысить MTU.
4. **Координаты (`0x02`) + голос (`0x03`)** на отправке (хост) и приёме (клиент), со счётчиком поколений и фрагментацией; обработка «нового участника» (плитка рисуется по геометрии из RTP сразу, имя подтягивается из SIP-ростера позже).
5. **Атомарное применение координат к кадру** (боковой канал метки + устранение гонки при «нарезке»).
6. **Гибридная развязка:** отключение SIP-отправки перенесённых полей при согласованном extmap; остальное (ростер «индекс→участник», декор + `confOrder`) остаётся на SIP.
7. **Совместимость и откат:** если пир не подтвердил extmap — работаем по-старому (SIP `confInfo`).

Этап 1 полностью изолирован; этап 2 снимает главный риск (сосуществование с управлением перегрузкой); этапы 3 даёт самостоятельную пользу (A/V-синхронизация); этапы 4–5 закрывают исходную проблему артефактов; этап 6 — финальная очистка.

## 6. Итог

- **Что делаем:** переносим синхронно-критичные метаданные конференции (координаты, голос, метка A/V-синхронизации) с SIP на RTP-расширения (RFC 8285), где они синхронизированы с кадром по построению.
- **Почему:** устраняет гонку «видео новое — координаты старые» и убирает костыли (throttle из-за флуд-защиты SIP).
- **Как:** согласование по SDP (`extmap`), вставка/чтение расширений в `socket_pair.cpp` (без патча FFmpeg), двухбайтовый формат RFC 8285 (профиль `0x1000`).
- **Что учесть:** это не только смена транспорта — нужны компактное расширение под MTU (пакет ≤ ~1200 байт, резерв ≈128 байт; URI выносится на SIP, координаты пагинируются), гибридная развязка с SIP, привязка «индекс → поток» по SIP, боковой канал для метки времени (декодер её затирает), счётчик поколений и откат для несовместимых пиров.

Предложение коллеги по формату (`0x1000`, события `ID/длина/данные`, дублирование 3×, строки `extmap`) **соответствует стандартам RFC 3550/RFC 8285** и берётся за основу. Детали для разработчика — в техническом плане `docs/rtp-extensions-conference-metadata-plan-en.md`.
